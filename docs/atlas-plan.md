# PixelHyd Atlas — plan

An illustrated, isometric "Atlas" view of one district, switchable with the existing Interactive Map.
The architecture was approved on 2026-11-26. AI image generation is **deferred** until the AI-free prototype
has been reviewed. The audit is in [audit-2026-11.md](audit-2026-11.md).

## 1. What the repository already gives us

- The Interactive Map is already a deep-zoom image viewer. MapLibre GL draws a raster pyramid (PMTiles) in
  image space, and `web/src/lib/projection.ts` maps WGS84 → UTM 44N → art pixels → image-space lon/lat
  exactly. It is tested against pyproj (`pipeline/.../iso.py`, `web/src/lib/projection.test.ts`).
- The pipeline renders any UTM region in that projection from validated features (`scene.py`, `render.py`),
  and chunked rendering is seam-safe.
- Stable ids already exist: Overture building ids, OSM ids, company site ids (`corporate.json`) and place
  ids (`places.json`).
- The view state (lat, lon, zoom) is written to the URL on every move, and `MapView` reads it on mount.

## 2. Approved architecture

| Part | Decision |
|---|---|
| Viewer | A second, **isolated** MapLibre instance in `web/src/atlas/AtlasViewer.tsx`, lazy-loaded (`React.lazy`), over the Atlas PMTiles. No new dependency. `MapView.tsx` is not modified. |
| Only one WebGL context | While the Atlas is shown, `MapView` is **unmounted**. Switching back remounts it, and it restores its camera from the URL it already writes. App state (selection, home search, preferences) lives in `App.tsx` and survives the switch. |
| Art | A separate render path, `pipeline/src/hitec_pipeline/atlas.py`, with its own style module. It **reuses** `iso.py`, `scene.py` (scene building and painter's order) and the normalised features; it does **not** change `render.py` or `style.py`. |
| Geography | Same projection as the map (UTM 44N, 2:1 dimetric) at a higher scale (k = 8 px/m proposed). Lon/lat → Atlas pixel is the existing exact affine map, so no anchor warping or fitted transform is needed. |
| Manifest | `atlas/<district>/manifest.json`: artwork version, projection metadata, bounds, and hotspots that **reference** existing ids. Names and details are read from `corporate.json` and `places.json` at runtime, never copied. |
| Toggle | One segmented control, "Interactive Map / Illustrated Atlas", in the existing top bar, plus a URL parameter `v=atlas`. Hidden unless `VITE_ATLAS` is set **and** the manifest loads. |
| Scope inside the Atlas | Pan, zoom, a district label, a few hotspots with a small card, and "Open in Interactive Map". No search, home search or routing. |

## 3. First district

Tile **`r2c2`** (1 km², UTM 221224–222224 E, 1930824–1931824 N) contains the Cyber Towers junction
(17.4507 N, 78.3801 E), the centre of the original 5 km square. It has the densest validated data. Data
comes from the existing prepared tiles; nothing new is downloaded.

## 4. Directory structure

```
pipeline/src/hitec_pipeline/atlas.py         # render path: scene → Atlas art at k=8, own style
pipeline/src/hitec_pipeline/atlas_style.py   # Atlas palette, light and detail rules (separate from style.py)
pipeline/tests/test_atlas.py                 # projection reuse, determinism, seams, manifest validity
data/out/atlas/<district>/<version>/         # master PNG and tiles (not committed)
web/public/atlas/<district>/                 # published: manifest.json + atlas.<version>.pmtiles
web/src/atlas/AtlasViewer.tsx                # isolated viewer, own lifecycle
web/src/atlas/manifest.ts                    # types, loading, validation, hotspot → pixel
web/src/atlas/*.test.ts                      # transform, manifest validation, missing-asset fallback
```

`App.tsx` gets only the mode state, the toggle and the conditional mount.

## 5. Geographic accuracy strategy

- **Source of truth:** the existing normalised features (OSM and Overture with provenance). Nothing is
  placed by hand or by AI.
- **Verified structure:** building footprints, roads, water, parks and the district outline come straight
  from those features, through the exact projection.
- **Artistic approximation:** wall and roof materials, windows, vegetation detail and lighting. Labelled as
  such in the manifest (`"art": "generated by rules"`).
- **Check:** `test_atlas.py` rasterises the footprints and road centrelines from the features in Atlas
  pixels and compares them with masks taken from the Atlas render (footprint IoU, road overlap). It fails
  below a threshold.
- **Hotspot alignment:** each hotspot's lon/lat comes from the referenced feature (footprint centroid or
  place point). Its pixel is computed, never stored as truth. A cached pixel in the manifest is re-checked
  against the computation on every build.

## 6. Deep zoom

The Atlas master is rendered in chunks (as the map is), cut into 256 px WebP tiles, pyramided and packed
into one PMTiles archive. The existing `tiles.py` helpers (pyramid, merge, `pmtiles` writer) are reused
through the Atlas path. The browser never loads the master image.

## 8. Implementation phases (after review of each)

| Phase | Scope | Done when |
|---|---|---|
| B | District data check: confirm `r2c2` and its neighbours are prepared and valid; list the hotspot candidates by id | Report of counts and sources |
| C | Low-resolution style study (k = 4, 250 m) with `atlas_style.py` | Images for your review |
| D/E | Full 1 km² render at k = 8 → PMTiles + manifest | Accuracy check passes; size measured |
| F | `AtlasViewer` (isolated, lazy, its own cleanup) | Unit tests; no change in the map's bundle chunk |
| G | Hotspots by id (3–5: e.g. Cyber Towers, the Microsoft campus, a park, a metro station) | Transform tests; invalid ids are skipped and logged |
| H | Toggle, feature flag, missing-artwork fallback, camera restore | Switching both ways keeps state; Atlas off = map unchanged |
| I | Tests, measured load and memory, docs | Acceptance criteria below |

## 9. Acceptance criteria

- With `VITE_ATLAS` unset or the manifest missing, the app is byte-for-byte the current app (no toggle, no
  Atlas chunk loaded).
- Map → Atlas → Map restores the same centre and zoom; the selection and home search state are kept.
- Only one MapLibre map exists at any time (checked in a browser test).
- Hotspot pixels are within 1 Atlas px of the projection of their features.
- The footprint IoU between the Atlas render and the features is at or above the agreed threshold.
- `test_seams.py` and every existing suite still pass; `render.py` and `style.py` are unchanged.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Two WebGL contexts on the Intel iGPU | Unmount `MapView` while the Atlas is shown |
| Bundle growth | The Atlas is a lazy chunk; MapLibre is already shared |
| Art drift from geometry | The art is rendered from the features; the accuracy test fails the build |
| Scope creep into GIS features | The Atlas has no search, home search or routing by design |

## 11. Deferred: AI-assisted refinement

Only after the AI-free prototype is reviewed. Possible later approach: image-to-image with a geometry guide
(e.g. ControlNet) over the rule-based render, tile by tile, each checked against the feature masks.
- Local generation is impractical on this laptop.
- Free hosted GPUs are the likely route.
- Model licences (e.g. FLUX.1 [schnell] Apache-2.0, FLUX.1 [dev] non-commercial) must be re-checked at the
  time of adoption.
